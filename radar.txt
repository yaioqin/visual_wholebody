# B2-Z1 雷达遮挡下的 Whole-Body Reachable 方案

## 总体思路

保留当前论文兼容的控制结构：

- 策略仍只实际控制前 12 维腿部动作；
- 后 6 维 arm action 继续 mask 为 0；
- 机械臂仍由 EE 目标和 DLS IK 控制；
- 身体姿态通过腿部策略调整；
- arm reward 通过现有 `arm advantage -> leg PPO` 路径影响腿部策略。

本次重点不是简单增大 `mixing_ratio`，而是补齐以下闭环：

```text
雷达/连杆碰撞检测
-> 判断当前路径是否可行
-> 可行时正常跟踪
-> 不可行时暂停目标推进并给身体恢复窗口
-> IK/EE reward 反馈身体调整效果
-> 身体姿态恢复后继续跟踪
```

## 1. 碰撞与路径参考

### 雷达几何

把 B2 URDF 中 `base_link` 的前方圆柱碰撞体作为雷达：

```text
center = [0.34218, 0, 0.15851]  # base_link 局部坐标
radius = 0.076
height = 0.16
safety_margin = 0.03
```

碰撞计算使用膨胀后的圆柱，安全半径为 `0.106 m`，安全半高为 `0.11 m`。

机械臂 `link00` 到 `gripperMover` 使用 URDF 碰撞几何转换为保守的 capsule/sphere 近似。运行时只在初始化阶段解析 URDF，之后在 GPU 上批量计算：

- 每个机械臂连杆采样点到雷达圆柱的距离；
- 末端到雷达的距离；
- 当前机械臂最小安全距离；
- 当前身体姿态下的路径碰撞风险。

不新增独立雷达 actor，不改变 Isaac Gym 的场景结构。

### 目标采样

目标点如果本身位于膨胀后的雷达碰撞体内，直接拒绝并重新采样。最多尝试 64 次；仍失败时保留上一个合法目标，并记录 `invalid_goal_sample`。

目标点在雷达外部但直线插值穿过雷达时，不拒绝目标，因为这种情况应该由 whole-body controller 通过绕行或身体调整解决。

### 路径参考

对当前 EE 到目标点的路径进行 32 个采样点检测：

1. 先检查直线路径；
2. 若直线穿过雷达，生成四类候选绕行路径：
   - 左侧绕行；
   - 右侧绕行；
   - 上方绕行；
   - 下方绕行；
3. 每个候选路径都检查：
   - EE 路径是否碰撞；
   - 机械臂连杆近似体是否碰撞；
   - 关节位置是否超限；
   - 最小 clearance 是否大于 `0.03 m`；
4. 选择最短且 clearance 最大的合法路径。

这一步只负责生成安全 EE 参考，不替代腿部策略，也不直接求解全身关节。

### 当前姿态下无安全路径

如果当前身体姿态下没有合法的机械臂绕行路径：

- 保持机械臂在最后一个安全 EE reference；
- 暂停 `goal_timer`，不继续把目标推进到雷达另一侧；
- 设置 `goal_blocked = 1`；
- 给腿部策略保留最多 `2.0 s` 的身体恢复窗口；
- 如果身体姿态恢复后出现合法路径，继续执行；
- 如果 2 秒后仍不可行，记录一次 `goal_recovery_timeout`，对该目标施加失败惩罚并重新采样，不直接终止整个 episode。

这样可以避免机械臂被迫沿着必然穿过雷达的轨迹运动，同时允许腿部先蹲下、俯仰或横滚。

## 2. Actor/Critic 观测

在现有观测后追加以下 10 个量，并同时加入 actor 和 critic：

```text
goal_relative_to_radar      3
ee_relative_to_radar        3
min_arm_radar_clearance     1
direct_path_blocked         1
ik_position_residual        1

```

具体含义：

- 最终目标相对于雷达中心的位置；
- 当前 EE 相对于雷达中心的位置；
- 当前机械臂最小 clearance；
- 直线路径是否被雷达阻挡；
- 当前 IK 的位置残差；
- 是否处于身体恢复阶段。

## 3. Reward 设计

### 保留现有 reward

保留：

```text
arm_scales.tracking_ee_world = 0.8
```

并确保 `tracking_ee_world` 不再出现在腿部 `rewards.scales`，避免同一 EE reward 重复累计。

保留现有：

```text
mixing_schedule = [0.5, 2000, 2000]
```

第一轮不直接把 mixing ratio 提高到 1.0，因为当前失败不能仅归因于 mixing 太小；必须先让 arm advantage 获得正确的碰撞和恢复信号。

### 新增 arm-only reward

新增三个机械臂 reward，只放在 `arm_scales`：

```text
tracking_ee_final_blocked = 0.8
radar_clearance_violation = -1.0
recovery_progress = 0.5
```

含义：

1. `tracking_ee_final_blocked`

   只在 `goal_blocked=1` 时生效，计算当前 EE 到最终目标的误差，而不是到暂时保持的安全 reference 的误差。这样即使机械臂被暂时停在安全位置，腿部仍然能收到“最终目标没有完成”的信号。

2. `radar_clearance_violation`

   对最小 clearance 低于 `0.03 m` 的部分施加归一化惩罚。该项防止策略通过直接撞击雷达换取 EE tracking reward。

3. `recovery_progress`

   根据以下势函数的改善给奖励：

   ```text
   final_goal_error 是否下降
   min_clearance 是否增加
   ik_residual 是否下降
   ```

   只奖励相对上一个控制周期的改善，不奖励单纯大幅摆腿。

### PPO 处理

保留现有 additive mixing：

```text
leg_advantage + mixing_ratio * arm_advantage
```

同时新增日志：

```text
arm_advantage_mean/std
leg_advantage_mean/std
goal_blocked_rate
recovery_progress
recovery_timeout_rate
```

如果第一轮训练在碰撞率已下降但身体恢复仍不足，再进行唯一一轮受控对照：

```text
mixing_schedule = [1.0, 1000, 2000]
```

其他配置、随机种子和目标序列保持一致，用于判断是否确实需要更大的 arm advantage。

## 5. 验证与验收

### 几何单元测试

覆盖：

- 目标点位于雷达内部时被拒绝；
- 正前方目标但直线路径穿雷达时被标记为 blocked；
- 左绕、右绕、上绕、下绕路径的合法性判断；
- 机械臂连杆而非只有 EE 点撞雷达时能被检测；
- 身体高度变化后 clearance 和路径状态会重新计算。

### 固定场景回放

至少测试以下目标切换：

```text
右侧 -> 左侧
左侧 -> 右侧
正前方上方 -> 正前方下方
正前方下方 -> 侧面
```

其中正前方场景必须选择“目标点在雷达外部、直线路径被雷达挡住”的目标，不能把目标点放在雷达碰撞体内部。

每个场景运行 200 个 episode，记录：

```text
最终 EE 误差
目标成功率
最小雷达 clearance
连杆碰撞次数
goal_blocked_rate
平均恢复时间
base height/pitch/roll 变化
腿部 tracking reward
locomotion reward
```

验收标准：

- 目标点内部采样率为 0；
- 机械臂连杆与雷达的解析碰撞次数为 0；
- 正前方遮挡场景成功率相对当前 checkpoint 提升至少 30%；
- 成功样本的最终 EE 误差小于 `0.08 m`；
- 恢复阶段平均不超过 `1.5 s`；
- locomotion 失败率和姿态终止率不比当前模型增加超过 10%。

视频回放中额外显示：

- 雷达圆柱；
- 机械臂当前路径；
- 选中的绕行 waypoint；
- 当前最小 clearance；
- `goal_blocked` 和 recovery timer。

## 假设与边界

- 雷达被视为固定在 B2 `base_link` 上的圆柱；
- 目标点在雷达内部时定义为物理不可达目标，不要求策略强行完成；
- 纯平移不作为主要恢复动作，因为当前目标中心的 `x/y` 跟随 base；重点观察 base 高度、pitch、roll 以及机械臂绕行；
- 不解放 arm 后 6 维动作；
- 不引入外部全身求解器；
- 碰撞模块只生成安全参考和 reward/observation 信号，身体姿态仍由 PPO 学习。

    def _radar_clearance_for_points(self, points_world, extra_radius=0.0):
        """Signed clearance of world points from the B2 base-mounted radar cylinder."""
        num_points = points_world.shape[1]
        base_quat = self.base_quat[:, None, :].expand(-1, num_points, -1).reshape(-1, 4)
        radar_center_world = self.base_pos + quat_apply(self.base_quat, self.radar_center_local[None, :])
        local = quat_rotate_inverse(
            base_quat,
            (points_world - radar_center_world[:, None, :]).reshape(-1, 3),
        ).reshape(self.num_envs, num_points, 3)
        radius = self.radar_radius + self.radar_margin + extra_radius
        half_height = self.radar_half_height + self.radar_margin + extra_radius
        radial = torch.linalg.norm(local[..., :2], dim=-1)
        axial = torch.abs(local[..., 2])
        radial_gap = radial - radius
        axial_gap = axial - half_height
        outside = torch.sqrt(torch.clamp(radial_gap, min=0.) ** 2 + torch.clamp(axial_gap, min=0.) ** 2)
        inside = -torch.minimum(radius - radial, half_height - axial)
        return torch.where((radial_gap <= 0) & (axial_gap <= 0), inside, outside)

    def _load_arm_collision_radii(self):
        """Load conservative per-link bounding radii from the configured URDF."""
        fallback = self.arm_collision_radius
        radii = [fallback] * (len(self.arm_body_names) + 1)  # EE point, then rigid-body points
        urdf_path = getattr(self.cfg.asset, "file", "")
        urdf_path = urdf_path.replace("{LEGGED_GYM_ROOT_DIR}", LEGGED_GYM_ROOT_DIR)
        if not os.path.isfile(urdf_path):
            return torch.tensor(radii, dtype=torch.float, device=self.device)

        try:
            root = ET.parse(urdf_path).getroot()
            for point_idx, link_name in enumerate(self.arm_body_names, start=1):
                link = root.find(".//link[@name='%s']" % link_name)
                if link is None:
                    continue
                link_radius = fallback
                for collision in link.findall("collision"):
                    geometry = collision.find("geometry")
                    if geometry is None:
                        continue
                    sphere = geometry.find("sphere")
                    cylinder = geometry.find("cylinder")
                    box = geometry.find("box")
                    if sphere is not None:
                        link_radius = max(link_radius, float(sphere.attrib.get("radius", fallback)))
                    elif cylinder is not None:
                        radius = float(cylinder.attrib.get("radius", fallback))
                        length = float(cylinder.attrib.get("length", 0.0))
                        link_radius = max(link_radius, math.sqrt(radius * radius + (0.5 * length) ** 2))
                    elif box is not None:
                        size = [float(value) for value in box.attrib.get("size", "").split()]
                        if len(size) == 3:
                            link_radius = max(link_radius, 0.5 * math.sqrt(sum(value * value for value in size)))
                    # Mesh bounds are not available from URDF alone; retain the configured fallback.
                radii[point_idx] = link_radius
            # The grasp point is offset from gripperMover, so use that link's radius for the EE point.
            if self.arm_body_names:
                radii[0] = radii[-1]
        except (ET.ParseError, OSError, ValueError):
            # A missing or malformed URDF must not prevent non-collision tasks from starting.
            pass
        return torch.tensor(radii, dtype=torch.float, device=self.device)

代码中实际是：

- `waypoint_1`
- `waypoint_2`
- 最终目标

也就是两段中间绕行点。每一段路径又通过 `_path_clearance(..., samples=32)` 采样了 32 个碰撞检查点。

视频中的 10 个红色点只是起点到最终目标的球坐标插值，不是 10 个 waypoint，见 [`play_aliengo_z1_video.py:109`](/root/rivermind-data/visual_wholebody/low-level/legged_gym/scripts/play_aliengo_z1_video.py:109)。

对于“从左侧绕到右侧”的简单圆柱障碍，两级 waypoint 理论上已经足够：

```text
当前状态 -> 绕行点 1 -> 绕行点 2 -> 目标
```

增加到 10 个 waypoint 不会自动解决当前问题，因为当前主要失败原因是：

- 机械臂已经进入雷达安全体；
- planner 从一个已经碰撞的起点开始规划；
- 规划只检查 EE 中心点，没有检查整条 arm link 的扫掠区域。

这种情况下，即使增加到 10 个点，仍可能是：

```text
碰撞状态 -> 10 个碰撞或不可达的点
```

所以当前更应该增加“逃逸 waypoint”机制，并对 arm link 做 swept-collision 检查。若只是希望路径更平滑，可以把一条安全曲线离散成 10 个采样点，但不应把它们当成 10 个独立决策 waypoint。

2. 没有通过调整身姿来给 arm 腾出空间，不能简单归因于“模型还没学会”。

当前训练确实允许腿部策略间接受到 arm reward 的影响，但没有显式训练“遇到雷达遮挡时主动蹲下、侧身或调整 body pose”：

- arm 输出在 [`manip_loco.py:146`](/root/rivermind-data/visual_wholebody/low-level/legged_gym/envs/manip_loco/manip_loco.py:146) 以后由 IK 控制；
- PPO 的后 6 维 arm action 在 [`manip_loco.py`](/root/rivermind-data/visual_wholebody/low-level/legged_gym/envs/manip_loco/manip_loco.py:120) 被置零；
- 腿部只能通过混合后的 arm advantage 间接受到 EE tracking 信号；
- `recovery_progress` 和 `radar_clearance_violation` 只是间接的 clearance reward；
- 当前 `workspace_radar` 还继承了 `feet_height=0.0`、`walking_dof=0.9`，没有专门鼓励前腿主动下蹲或改变 body posture。

因此更准确的判断是：

> 当前模型既没有充分学会 body recovery，也没有被明确教会在“arm 已经被雷达挡住”时调整身体姿态。

```text
waypoint=1

```

```text

```

1. **路径参考本身是跳变的**

在 [`manip_loco.py:1730`](/root/rivermind-data/visual_wholebody/low-level/legged_gym/envs/manip_loco/manip_loco.py:1730) 中，planner 一旦激活，就直接把 IK 目标设为 waypoint：


而 IK 的位置误差直接在 [`manip_loco.py:146`](/root/rivermind-data/visual_wholebody/low-level/legged_gym/envs/manip_loco/manip_loco.py:146) 计算：

```python

```

因此 waypoint 距离较大时，机械臂会产生较大的瞬时动作。`_path_clearance(..., samples=32)` 的 32 个点只是碰撞检测采样，不是控制轨迹点。

建议改为：

- 保留当前候选路径选择；
- 把选中的三段折线路径按弧长重新采样成最多 8 到 10 个点；
- 相邻点距离限制在约 `0.05~0.08 m`；
- 增加 `waypoint_index`，每次只追踪下一个点；
- 到达当前点后再切换下一个点；
- 每个点切换时保留最小 clearance；
- 必要时对折线拐角做圆滑过渡，但过渡后的曲线仍要重新进行碰撞检查。

这样 10 个点表示的是一条平滑、受步长限制的参考轨迹，而不是 10 个独立的突变目标。

第二个问题，**不能简单认为只是 model 4000 还没学会调整身体姿态**。

当前确实存在“训练还早”的因素，但不是唯一原因：

- `mixing_schedule=[0.5, 2000, 2000]`，4000 iteration 才刚达到最大 `0.5` 混合比例；
- arm action 在 [`manip_loco.py:120`](/root/rivermind-data/visual_wholebody/low-level/legged_gym/envs/manip_loco/manip_loco.py:120) 被置零，机械臂实际由 IK 控制；
- 腿部只能通过 arm advantage 间接受到 EE reward 的影响；
- `workspace_radar` 继承的是 `feet_height=0.0`、`walking_dof=0.9`，并没有明显鼓励前腿主动下蹲或改变姿态。

更关键的是：雷达和机械臂基座都固定在机器人机身上。当前目标和 waypoint 也是相对于机身定义的。因此单纯让机身 roll/pitch 或上下移动，并不会显著改变“机械臂相对于雷达”的几何关系。身体姿态可以帮助地面稳定性、目标相对世界位置和 IK 可行性，但不能替代机械臂绕过一个固定在机身上的雷达。

所以结论是：

- **不需要单独增加一个 body-recovery policy 模块**，whole-body PPO 理论上可以保留；
- 但不能期待仅靠继续训练就自动学会绕雷达，因为当前参考路径只保证 EE 中心点，且 body action 对 base-mounted radar 的相对几何作用很弱；
- 必须先提供平滑、可行、对整条 arm link 做过碰撞验证的参考路径；
- 之后再观察 leg advantage 是否学会配合。如果仍没有 body 调整，再考虑增加更明确的 body/leg clearance 或姿态 reward。

当前正在运行的训练进程不会自动加载这些 planner 修改；平滑 waypoint 实现完成后，需要用新实验重新训练或至少重新回放验证。
